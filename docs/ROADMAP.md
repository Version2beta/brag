# BRAG roadmap

Phase 1 is implemented. Phase 2 emits schema v2 because its required `engineering_evidence` field is incompatible with Phase 1 schema v1; the v1 schema remains available for existing reports. Phase 2 static Go measurements are accepted with documented limitations after controlled fixture, schema-instance, reproducibility, and bounded performance checks. Duplication and vulnerability scanning remain explicitly unavailable/not run, and non-Go source analysis is unsupported. Phase 3A provides an opt-in dynamic Go test evidence slice accepted with documented limitations. Phase 3B.1 bounded mutation testing and the Phase 3B.2 bounded test-contribution experiment are accepted with documented limitations. Phase 4A implements a bounded static-only Pi `/brag` and `/brag all` extension; further Phase 4 reasoning work and Phase 5 remain unimplemented. See [Phase 4 readiness and boundaries](PHASE4-READINESS.md).

## Phase 1 — Deterministic foundation (completed)

- CLI commands and branch/repository scope selection.
- Contributor identities, Git authorship and coauthor attribution, and tracked working-tree overlay.
- Explicit denominators, cumulative churn versus snapshot net change, and versioned evidence schema.
- Acceptance: deterministic JSON; reliable base selection with pinned merge-base provenance; only HEAD-reachable commits in repository scope; local tracked changes distinct from committed measurements; untracked content excluded; identity and attribution methods explicit; unavailable evidence represented explicitly; controlled reproducibility and Git-fixture tests.

## Phase 2 — Static engineering measurements (accepted with documented limitations)

- Implemented stage: custom `brag-go-ast-v2` function metrics (cyclomatic, cognitive, maximum control nesting, physical lines), deterministic distributions and thresholds, and stable-key function comparisons for base/HEAD/current tracked overlay (all scope: HEAD/current). Git blobs use `ls-tree`/`cat-file`; no checkout occurs. Limits, parse failures, partial status, capped changed-function detail, and identity ambiguity are disclosed. Complexity evidence is repository-wide and not attributed to a person.
- Implemented next stage: tracked Go test snapshot inventory for valid top-level test/benchmark/TestMain/example conventions, subtest call sites, table-driven structural heuristic, test-to-production ratio, and stable-key/full-declaration-hash comparisons. Bounded first-parent history compares changed test-file definitions; roots compare to empty, merges are excluded and make status partial, and authors/coauthor trailers resolve through Phase 1 aliases. Selected/all introduced-test ratios have explicit denominators. The current overlay is separate and never attributed.
- Implemented documentation stage: package/exported symbol/interface method comment-presence ratios; tracked documentation content-hash additions/removals/modifications; canonical generated markers, `go:generate`, and documented template/config patterns. Generation is never run; non-marked documentation is `unknown`, not asserted hand-authored. This evidence is not quality or person attribution.
- Implemented architecture stage: tracked Go package snapshots from Go AST plus tracked root `go.mod` module path; direct internal/external imports, separate test-only imports, fan-in/out and dependency distributions, transitive-only internal reachability excluding direct imports, strongly connected cycle groups, and stable baseline/HEAD/current comparisons. Package and edge details are deterministic and capped; parse-failure path lists cap at 50. Build tags, replace directives, unresolved internal paths, parse failures, and file/byte limits and the 50-path parse-failure list cap are disclosed. This is import-graph coupling only: no `go list`, dependency resolution, runtime coupling, or module download.
- Implemented security stage: direct `go.mod` requirement/version inventory and bounded source-location indicators for crypto/weak crypto imports, `net/http` server/handler signatures and registration, `os/exec` calls, syscall/privilege APIs, `unsafe`, and lexical auth/authz-related identifiers. Dependency declaration changes compare across snapshots. Indicators do not establish vulnerabilities, reachability, exploitability, or runtime behavior. Vulnerability scanning is explicitly unavailable/not_run: no scanner/advisory data is integrated and no network is used.
- `duplication` is explicitly unavailable/unmeasured; no simplistic source-text metric is used. Non-Go AST analysis remains unsupported; recognized non-Go source extensions are counted in each applicable snapshot. See the acceptance decision below for category decisions and evidence.
- No vulnerability database/scanner, generator, analyzed-repository code execution, dependency resolution/download for the analyzed repository, or network access is used. Scores are custom static indicators, not standard metrics or evidence of reasoning difficulty.

## Phase 4 — Reasoning integration (Phase 4A implemented; remaining work not implemented)

**Phase 4A boundary:** the Pi extension validates only default static schema-v2 reports and sends a bounded evidence projection to the configured model; it performs no additional source inspection and defines no separate report schema. This does not support broad claims about PRs/reviews, maintainability, duplication, test effectiveness, reliability, developer impact, or vulnerability absence. Future-work boundaries and the evidence sufficiency matrix are in [docs/PHASE4-READINESS.md](PHASE4-READINESS.md).

- Phase 4A implemented: Pi `/brag` and `/brag all` invoke only the default static CLI with a fixed scope, validate schema v2, and present a limited evidence summary. See the usage/configuration details in [README.md](../README.md) and security limits in [PHASE4-READINESS.md](PHASE4-READINESS.md).
- Remaining proposed work, not started: broader evidence-first reasoning beyond the bounded Phase 4A summary; bounded additional source inspection; contract fidelity; behavioral adequacy; security interpretation; reasoning simplicity; context locality; verification confidence; orientation; and agentic readiness. No `$brag` command is implemented.
- Future work only: keep schemas v1–v5 unchanged; any separately versioned evidence-linked reasoning report is not part of Phase 4A. Preserve unavailable, partial, not-run, and measured-zero distinctions; do not produce a composite score or unsupported claim.
- Default integration must not execute analyzed-repository tests or programs, run generators or scanners, resolve dependencies, or use the network. Dynamic, mutation, and contribution analysis remain separate explicit user choices; test execution is unsandboxed and may use host APIs/network.
- Phase 4A boundary: only schema-v2 default static reports are accepted; no sidecars, source inspection, dynamic flags, separate report schema, or Phase 5 calibration are implemented. It sends a bounded evidence projection to Pi's configured model provider. Seven focused stub-Pi harness tests passed against each of two controlled fixtures; the extension was not run in a live Pi session and no provider/model request was made. Further acceptance criteria above apply to remaining work, not Phase 4A.

## Phase 3B.1 — Bounded mutation testing (accepted with documented limitations)

Mutation execution uses fresh disposable copies of tracked snapshots for the baseline control and each mutant; test writes cannot contaminate later runs. It is a separate explicit `--mutation-tests` workflow (mutually exclusive with `--dynamic-tests`) and emits schema v4; static defaults and v1-v3 remain unchanged. It reuses Phase 3A disposable tracked snapshots, offline Go environment, process-group cleanup, timeouts, private external artifacts and output caps. Branch default selects HEAD; all selects current tracked worktree; explicit snapshot choices are branch baseline/HEAD/current tracked. Untracked content is excluded. `brag-go-mutation-v1` changes exactly one comparison/logical/boolean token; boolean swaps are selected only when Go object resolution proves an unshadowed predeclared constant reference; declarations, shadowed uses and selector names are excluded. Stable IDs determine lexicographic selection; 20 mutants/snapshot default, maximum 50, 10,000 scanned candidates/snapshot. Package/path filters do not narrow the `go test ./...` population. Package filters require the tracked root go.mod module path. Generated, vendor, test, nested-module, Go-ignored, platform-suffixed, build-constrained files, and unsafe boolean identifier references are disclosed as skipped; malformed/oversize files mark population incomplete. Known eligible/unselected and unknown population incompleteness are separate. Summary counts classify killed/survived/invalid/inconclusive/not_executed; only a passing control followed by valid test failure is killed. Score denominator is killed+survived and zero denominator is null/unavailable. Manifest is deterministic; execution outcomes are separate and volatile. No individual-test marginal contribution or developer attribution is claimed.

Per-run and total timeout defaults are 2m/10m, maxima 10m/30m; report provenance includes host GOOS/GOARCH, both timeout values, and fixed `go test -json -count=1 -shuffle=off ./...` settings. Output is capped at 1 MiB per stream and artifacts at 96 MiB aggregate. Tests execute arbitrary code with host-user privileges and may use the network; offline module lookup is not a sandbox. Mutation operators are syntax-level substitutions, not equivalence proofs. Candidate discovery follows the `go test ./...` package population and excludes/reports nested modules, Go-ignored directories, platform-suffixed files, build-constrained files, and boolean identifiers that cannot be resolved safely; malformed or scan-capped source can leave population completeness unknown. Example score: 4 killed / (4 killed + 8 survived) = 0.333; invalid and inconclusive cases do not enter denominator. The Phase 3B.2 contribution experiment is accepted with documented limitations as noted above; Further Phase 4 reasoning remains separate.

### Phase 3B.1 acceptance decision

Accepted with documented limitations. Controlled temporary Git fixtures cover control gating and kill/survive results; branch/all snapshots and untracked exclusion; stable selection and source filters; timeouts, cancellation and artifact bounds; manifest/outcome persistence; and static opt-out. Regression tests cover compile/setup and mixed test/build failure evidence, and reject unknown package-level output mixed with a test failure. Offline schema-instance validation accepted v1-v4 reports and v4 manifest/outcome artifacts using cached `github.com/google/jsonschema-go` v0.4.2. Final offline checks on Go 1.27.2 darwin/arm64 passed: formatting, `go test -count=1 ./...`, `go vet ./...`, build, and Linux/Windows test-binary cross-compilation. Independent review found no issue in the killed-result path; it noted that the mixed-output regression exercises the accounting gate directly, not an end-to-end injected subprocess case. The final classifier fix changed neither schemas nor serialized report/artifact structures. This checkout has no `.git` metadata, so its status/staged state and integration against its own history could not be inspected; acceptance exercised temporary Git fixtures.

Mutation tooling evaluation found no installed `go-mutesting` executable. Bounded searches of the local Go module cache/download cache found no go-mutesting or other identifiable Go mutation-testing module, so locally cached documentation/source for those tools was unavailable; no upstream capabilities are claimed. No tool installation, dependency or external hook was added. The in-repository runner was selected to reuse exact materialized snapshots, Go token positions, local deterministic selection and Phase 3A process controls without tool download or hidden mutation hooks.

### Phase 3B.2 acceptance decision

**Accepted with documented limitations** for the bounded, opt-in test-contribution evidence slice. The decision covers detection evidence for one selected mutation snapshot and comparable branch-baseline populations; it does not establish causal defect detection, test quality, or developer impact.

| Area | Decision | Evidence and boundary |
|---|---|---|
| Test identity and selector controls | Accepted with limits | Top-level conventional `TestX` identities include package, file, name, and full declaration SHA-256. | Detection, uniqueness, and marginal evidence | Accepted with limits | Mutation-keyed detector counts, per-test counts, overlaps, and suite-interaction comparisons are covered by focused calculation fixtures. | Bounds and private evidence | Accepted with limits | Limits are 200 tests per population, 1,000 pairs across populations, 1–3 repeats, at most 5 minutes per evaluation and 30 minutes total; output/artifact bounds reuse Phase 3 limits. History is capped at 500 commits, 100 changed test files/commit, 5,000 files, and 20 MiB of changed-test blobs; cached module identity metadata is capped at 32 MiB. | Schema and artifact integrity | Accepted | An offline JSON Schema validator using cached `github.com/google/jsonschema-go` v0.4.2 accepted a generated v5 report and contribution matrix. | Regression/build validation | Accepted on tested host | Final offline full-suite tests, `go vet`, build, formatting, deterministic calculation repeatability, and Linux/Windows test-binary cross-compilation are recorded with this acceptance review. Tests and opt-in execution used controlled temporary fixtures on Go 1.27.2, Darwin arm64; Linux/Windows runtime behavior was not exercised. |
| Repository state | Limitation | This checkout has no `.git` metadata, so its source revision, status/staging, and integration against its own history cannot be verified. Temporary Git fixtures exercised historical paths; no Git metadata was initialized here. |

**Safety:** opt-in test execution runs arbitrary repository test code with the current user's host privileges and is not sandboxed. Offline Go module lookup does not prevent test code from using the network. Do not run contribution mode on untrusted repositories; keep the explicitly configured artifact directory private and outside the repository. This decision does not extend the implemented Phase 4A boundary.
